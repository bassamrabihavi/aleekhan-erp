## 1. Context

The handoff ADR proposes Python 3.12+ / Django 5.2 LTS / DRF, React + TypeScript strict + Vite + React Router +
TanStack Query, PostgreSQL 17, Celery + Redis, private object storage with SHA-256, `ezdxf` in a sandbox,
OR-Tools only for capacity decisions, OpenTelemetry-compatible observability, JSON over HTTPS with versioned
OpenAPI 3.1, a modular monolith (no microservices, no second backend), and pinned minor/patch versions with SBOM
and dependency scanning in CI. It asks that the framework choice be confirmed in PHASE_00 and the ADR signed.

## 5. Consequences

- One backend codebase with module boundaries; cross-module writes go through services/outbox, never direct table
  writes (R09).
- PostgreSQL-specific features (triggers, partial indexes, regex CHECKs, least-privilege roles) are part of the
  contract; another database would need a new ADR.
- Upgrades follow the 14-day pin rule and must pass the full CI (lint, type, tests, migration round-trip,
  contract, authz, E2E, scans) before acceptance; SBOMs are produced each run.
- The public repository makes the secret scan and the review of every data/fixture diff the main barrier against
  data leaks; nothing private may ever be committed.
- The deviations D3-D8 and D11 must be closed or re-justified when the phase that needs them starts.

## 6. Alternatives considered

FastAPI + SQLAlchemy (suitable for computational services, but authorization, workflow and admin would have to
be built by hand) and .NET / SQL Server (closer to Windows automation, but needs a bridge to the existing
Python/DXF tooling) - both rejected in DEC-001 / DEC-039 (handoff ADR comparison).
