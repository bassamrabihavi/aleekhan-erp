# راهنمای آزمون پذیرش کاربر (UAT) — فاز ۱، گام ۰۱.۵ (رابط کاربری)

> محیط آزمایشی — داده ساختگی. همه کاربران، واحدها و اسنادی که در این آزمون می‌سازید ساختگی‌اند. داده واقعی کارخانه،
> نام واقعی کارکنان یا رمز واقعی وارد نکنید.

## ۱. آنچه لازم است
- همین مخزن روی رایانه (آخرین `git pull`)، Python محیط `.venv`، Node.js 24 و PostgreSQL آزمایشی (127.0.0.1:5433).
- برنامه احراز هویت روی گوشی (Google Authenticator یا Microsoft Authenticator) برای ورود دومرحله‌ای (DEC-050).
- مرورگر Edge یا Chrome.

## ۲. راه‌اندازی (یک بار برای هر جلسه آزمون)
در Git Bash، از پوشه مخزن:

```bash
# ۱) اتصال به پایگاه داده آزمایشی (رمز در فایل محلی است و نمایش داده نمی‌شود)
set -a; . /f/aleekhan/tools/pg-test.env; set +a
export PGDATABASE=aleekhan_uat
/f/aleekhan/tools/pgsql/bin/psql -d postgres -c "CREATE DATABASE aleekhan_uat ENCODING 'UTF8' TEMPLATE template0"

# ۲) ساخت جدول‌ها و داده پایه مصوب (نقش‌ها، ماتریس دسترسی v1.2، پارامترها)
cd backend
export ALEEKHAN_ENV=dev
export ALEEKHAN_INTERNAL_CIDRS=127.0.0.1/32          # فقط برای آزمون محلی: رایانه خودتان «شبکه داخلی» حساب شود
export ALEEKHAN_DOCUMENT_STORAGE_ROOT=/f/aleekhan/uat-files   # پوشه‌ای بیرون از مخزن برای فایل‌های قرنطینه
mkdir -p /f/aleekhan/uat-files
# کلید رمزگذاری ساختگی برای کلید TOTP و فایل‌ها (تصادفی، فقط برای همین آزمون؛ چاپ نمی‌شود). همین پنجره را تا پایان آزمون
# نگه دارید: اگر کلید عوض شود، ورود دومرحله‌ای ساخته‌شده دیگر خوانده نمی‌شود.
export ALEEKHAN_DATA_KEYS="uat:$(../.venv/Scripts/python.exe -c 'import base64, secrets; print(base64.urlsafe_b64encode(secrets.token_bytes(32)).decode().rstrip("="))')"
export ALEEKHAN_DATA_KEY_CURRENT=uat
../.venv/Scripts/python.exe manage.py migrate

# ۳) ساخت مالک سامانه از کنسول سرور (DEC-003 / DEC-054). رمز یک‌بارمصرف را دو بار می‌پرسد و نمایش نمی‌دهد.
../.venv/Scripts/python.exe manage.py bootstrap_owner --username syn.owner \
    --display-name "مالک ساختگی (محیط آزمایشی — داده ساختگی)" --reason "UAT 01.5"

# ۴) اجرای سرور (این پنجره را باز نگه دارید)
../.venv/Scripts/python.exe manage.py runserver 127.0.0.1:8000
```

در یک پنجره Git Bash دیگر:

```bash
cd frontend
npm ci        # فقط بار اول
npx vite      # رابط کاربری روی http://127.0.0.1:5173
```

نشانی آزمون: **http://127.0.0.1:5173/** — صفحه «وضعیت زیرساخت» بدون ورود: **http://127.0.0.1:5173/#/status**

اختیاری (برای دیدن Job در صفحه ۳۶): در پنجره سوم، از پوشه `backend` با همان متغیرهای مرحله ۱ و ۲:
```bash
../.venv/Scripts/python.exe manage.py shell -c "from platform_core.engine.context import Actor, RequestContext; from platform_core.jobs import service as j; c=RequestContext(Actor.system()); j.enqueue(c, job_type='session_expiry_sweep', task_key='uat-sweep-1'); j.enqueue(c, job_type='db_backup', task_key='uat-backup-1'); j.run_job('audit_integrity_check', task_key='uat-integrity-1')"
```

## ۳. مراحل آزمون

### ۳.۱ ورود نخست مالک
1. در http://127.0.0.1:5173/ نام کاربری `syn.owner` و رمز یک‌بارمصرفی که در مرحله ۳ ساختید را وارد کنید.
2. انتظار: صفحه «تعویض رمز عبور». رمز تازه (حداقل ۸ نویسه با حرف بزرگ لاتین، عدد و نماد) بگذارید.
3. انتظار: «فعال‌سازی ورود دومرحله‌ای» → «شروع فعال‌سازی» → کلید نمایش‌داده‌شده را در برنامه گوشی وارد کنید → کد شش‌رقمی را
   بزنید → **ده کد بازیابی** فقط یک بار نمایش داده می‌شود؛ یادداشت کنید → «ادامه».
4. انتظار: پیشخوان با نام شما و منوی سمت راست (همه بخش‌ها). نوار زرد «محیط آزمایشی — داده ساختگی» بالای صفحه.
5. یک بار هم رمز اشتباه بزنید (پس از خروج): پیام عمومی «اطلاعات ورود نادرست» با کد خطا و شناسه درخواست؛ هیچ اشاره‌ای به
   «کاربر پیدا نشد» نیست.

### ۳.۲ درخت سازمانی (منو: «درخت سازمانی»)
1. «واحد تازه» → کد `syn_co`، نام «شرکت ساختگی»، سطح «شرکت»، بالادست «ریشه»، دلیل → ثبت. چون این اقدام MFA تازه لازم دارد،
   پنجره «تأیید دومرحله‌ای لازم است» باز می‌شود: کد برنامه گوشی را بزنید.
2. یک «اداره» زیر آن، یک «سمت تازه» با تیک «رئیس واحد» (ظرفیت خودکار ۱ و غیرقابل تغییر)، و «انتصاب فرد به سمت» (شروع: همین
   لحظه؛ تاریخ گذشته ممکن نیست).
3. با صفحه‌کلید: روی درخت Tab بزنید؛ بالا/پایین جابه‌جا، «راست» بستن، «چپ» باز کردن، Enter انتخاب واحد (تغییر نام / غیرفعال).

### ۳.۳ امنیت و کاربران (صفحه ۴۶)
1. «کاربر جدید» → نام کاربری مثل `syn.docs`، نام نمایشی «مسئول اسناد ساختگی»، دلیل → «ساخت کاربر».
2. انتظار: پنجره «رمز یک‌بارمصرف»؛ با Escape بسته نمی‌شود؛ پس از تیک «یادداشت کردم» بسته می‌شود و **دیگر هرگز** نمایش داده نمی‌شود.
3. یک کاربر دیگر مثل `syn.approver` بسازید.
4. زبانه «انتساب نقش» → «انتساب نقش تازه»: به `syn.docs` نقش «مسئول اسناد» بدهید → وضعیت «فعال».
5. به `syn.approver` نقش «تأییدکننده درخواست‌ها» بدهید → هشدار «نیازمند تأیید نفر دوم (DEC-032)» و وضعیت «در انتظار تأیید نفر دوم».
6. اگر کاربر خودتان را انتخاب کنید، دکمه ثبت تا تیک «این نقش را به خودم انتساب می‌دهم» غیرفعال می‌ماند (DEC-003).
7. زبانه «کاربران» → «جزئیات» یک کاربر: باز/بسته کردن، باز کردن قفل، بازنشانی رمز (رمز یک‌بارمصرف تازه، یک بار)، بازنشانی MFA،
   ابطال همه جلسه‌ها — هر کدام دلیل می‌خواهد.
8. زبانه «نقش‌ها و مجوزها» → `owner_admin`: باید `platform.workflow.approval.decide`، `platform.document.approve` و
   `platform.config.parameter.publish` را ببینید (DEC-056، ماتریس v1.2 از گام ۰۱.۶).

### ۳.۴ کارها و تأییدها (صفحه ۳۹)
1. صندوق «نیازمند تصمیم من»: درخواستی که خودتان ثبت کرده‌اید اینجا نیست (هیچ‌کس درخواست خودش را تأیید نمی‌کند).
2. صندوق «درخواست‌های من» → کارت «انتساب نقش دارای حق تأیید» → «اقدام روی این درخواست»: دکمه «تأیید» عادی نیست؛ دکمه
   «تأیید اولیه نخستین دارنده (DEC-055)» هست. با دلیل تأیید کنید → وضعیت «تأییدشده» با برچسب «تأیید اولیه مالک».
3. «پس گرفتن درخواست» برای درخواستی که دیگری ثبت کرده باشد وجود ندارد؛ فقط درخواست‌دهنده می‌تواند پس بگیرد (با دلیل).

### ۳.۵ پارامترها (صفحه ۴۲)
1. ردیف `password_initial_validity_hours` → «تاریخچه و تغییر» → «ثبت و انتشار مقدار تازه» → همان ۷۲ با دلیل → منتشر می‌شود
   (سیاست مالک، یک گام). مقدار قبلی «جایگزین‌شده» می‌شود.
2. پارامتر «قاعده کسب‌وکار» هنوز در داده پایه وجود ندارد؛ اگر پیامی با «این قاعده هنوز تصویب نشده است (DEC-…)» دیدید، یعنی سرور
   درست آن را مسدود کرده است.

### ۳.۶ سلامت سامانه و Job (صفحه ۳۶)
1. وضعیت اجزا، شمارنده‌های رویداد خروجی/Job/ورود ناموفق از سرور؛ «یکپارچگی زنجیره ممیزی: سالم» (اگر Job بررسی اجرا شده باشد).
2. Job «پشتیبان‌گیری پایگاه داده»: «Job محافظت‌شده — لغو نمی‌شود».
3. Job «پایان جلسه‌های منقضی» در صف → «پایان امن» → دلیل → وضعیت «لغوشده».

### ۳.۷ اسناد (صفحه ۴۰) با کاربر مسئول اسناد
1. «خروج» → با `syn.docs` و رمز یک‌بارمصرفش وارد شوید → تعویض رمز (این نقش MFA لازم ندارد).
2. منو فقط «اسناد»، «جلسه‌های من» و … را نشان می‌دهد؛ «امنیت و کاربران» نیست. اگر نشانی `#/security` را دستی باز کنید:
   «به این بخش دسترسی ندارید».
3. «ثبت سند» → نوع `syn_drawing`، عنوان، محرمانگی S1 → صفحه سند → یک PDF ساختگی بارگذاری کنید → «قرنطینه (منتظر بررسی ضدبدافزار)»
   و دکمه «دانلود» غیرفعال (فقط نسخه پاک دانلود می‌شود؛ ClamAV در این محیط محلی نصب نیست، پس فایل در قرنطینه می‌ماند).
4. یک فایل `.exe` یا `.xlsm` بارگذاری کنید → خطای «نوع فایل مجاز نیست» (کد `FILE_TYPE_NOT_ALLOWED`).

### ۳.۸ جلسه و اندازه صفحه
1. «جلسه‌های من»: جلسه همین مرورگر مشخص است؛ جلسه‌های دیگر را با دلیل ببندید.
2. در مرورگر دیگری با همان کاربر وارد شوید، سپس از جلسه اول آن جلسه را ببندید؛ در مرورگر دوم با اولین کلیک به صفحه ورود با پیام
   «جلسه شما پایان یافته است» برمی‌گردید.
3. پنجره مرورگر را باریک کنید (یا F12 → حالت موبایل ۳۹۰ پیکسل): منو پشت دکمه «منو» می‌رود و جدول‌ها کارتی می‌شوند.

### ۳.۹ مالک درخواستِ شخص دیگر را مستقیم تصمیم می‌گیرد (DEC-056، از گام ۰۱.۶)
پیش‌نیاز: بخش ۳.۷ انجام شده و سند `syn_drawing` با نسخه ۱ در قرنطینه است. چون ClamAV روی این رایانه نیست، در پنجره سوم (از پوشه
`backend`، با همان متغیرهای مرحله ۱ و ۲) بررسی‌کننده **آزمایشی** را اجرا کنید؛ این فقط برای محیط آزمایشی است و در سرور واقعی
فقط ClamAV فایل را آزاد می‌کند:
```bash
../.venv/Scripts/python.exe manage.py shell -c "from platform_core.documents import scanner, service; print(service.scan_pending(scanner.FakeScannerForTests()))"
```
1. با `syn.docs` وارد شوید → «اسناد» → سند ساختگی → نسخه ۱ اکنون «پاک» است → «ارسال برای بازبینی» → یادداشت → وضعیت «در بازبینی».
2. «خروج» → با `syn.owner` وارد شوید → «کارها و تأییدها» → صندوق «نیازمند تصمیم من»: کارت «تأیید نسخه سند» با منبع
   `document_revision` و درخواست‌دهنده‌ای غیر از «شما» دیده می‌شود.
3. «اقدام روی این درخواست» → «تأیید» → یادداشت → کد دومرحله‌ای → وضعیت «تأییدشده». در صندوق «همه» و فیلتر «تأییدشده» کارت با
   یادداشت شما دیده می‌شود (ممیزی، نقش تصمیم‌گیرنده را `owner_admin` ثبت می‌کند).
4. دوباره با `syn.docs` وارد شوید → صفحه سند → نسخه ۱ «تأییدشده» است.
5. (اختیاری) رد: نسخه دیگری بارگذاری، بررسی آزمایشی و ارسال کنید؛ مالک با «رد» و دلیل آن را رد می‌کند → «ردشده».
6. کنترل منفی: اگر مالک نقش «مسئول اسناد» را به خودش بدهد (با تیک خودانتسابی) و خودش سندی بارگذاری و ارسال کند، آن درخواست در
   «نیازمند تصمیم من» نمی‌آید و تأیید آن خطای `SELF_APPROVAL_FORBIDDEN` می‌دهد (هیچ‌کس کار خودش را تأیید نمی‌کند).
7. پارامتر: انتشار مقدار پارامتر «قاعده کسب‌وکار» توسط مالک مجاز است ولی تا تصویب تصمیم همان پارامتر با پیام «این قاعده هنوز
   تصویب نشده است (DEC-…)» مسدود می‌ماند؛ انتشار مقدار پارامتر «فنی» برای مالک (بدون نقش تأییدکننده پارامترها) مجاز نیست.

### ۳.۱۰ سلامت تحویل رویدادها (صفحه ۳۶، از گام ۰۱.۶)
در «سلامت سامانه و Job» زیر شمارنده‌ها بخش «تحویل رویداد بین ماژول‌ها» آمده است: وضعیت «همه رویدادها تحویل شده»، «در انتظار
تحویل (زیر آستانه)»، «تأخیر در تحویل» یا «رویداد متوقف پشت dead letter»، تأخیر
قدیمی‌ترین رویداد (در این محیط پردازشگر پس‌زمینه اجرا نمی‌شود، پس رویدادها در انتظار می‌مانند و پس از ۱۵ دقیقه «تأخیر در تحویل»
نشان داده می‌شود — این درست است، نه خطا)، «جریان متوقف پشت dead letter»، «تعارض باز» و «جبران دستی لازم» (در این آزمون صفر).

```bash
/f/aleekhan/tools/pgsql/bin/psql -d postgres -c "DROP DATABASE aleekhan_uat WITH (FORCE)"
rm -rf /f/aleekhan/uat-files
```
